# Transversa — macOS iOS Development, Testing and App Store Publishing

**Tagline:** The ultimate converter  
**Companion documents:** `01-windows-development-and-publishing.md`, `02-agent-implementation-plan.md`, `04-ios-agent-implementation-plan.md`, `05-cross-platform-design-and-architecture.md`.

## 1. Purpose and prerequisites

Build a native iOS application with SwiftUI and Kotlin Multiplatform shared logic. Assumes access to a Mac running a supported macOS version, with a current stable Xcode and iOS SDK. Use an actual iPhone for codec/performance tests; the simulator is insufficient for hardware encoder verification.

- Install Xcode from Apple and open it once to accept the license and install components. Install Xcode Command Line Tools if needed.
- Install Git, a compatible JDK (use the KMP/Gradle compatibility matrix), and optionally Android Studio/IntelliJ IDEA for Kotlin development. Pin Kotlin, Gradle, KMP, Xcode and iOS deployment versions after a clean successful build.
- Join the Apple Developer Program for TestFlight/App Store distribution; configure App Store Connect, a unique bundle identifier, an Apple development team and automatic signing.
- Use a physical device with Developer Mode enabled for development testing, and representative iOS versions/devices for release QA.

Verify tools:

```bash
xcodebuild -version
xcrun simctl list devices available
java -version
./gradlew tasks
```

Select a specific installed Xcode if necessary with `xcode-select`; don't assume the latest Xcode is compatible with every pinned KMP version.

## 2. Project setup

Use a KMP shared module (`shared`) with `commonMain`, `androidMain`, and `iosMain` plus a native Xcode SwiftUI application (`iosApp`). Follow the official KMP **native UI** approach, not shared Compose UI. Export a Kotlin/Native framework (prefer an XCFramework for distribution) and link it to Xcode via the supported Gradle integration for the pinned KMP version. Avoid manual copying of frameworks that bypass dependency or architecture tracking.

Suggested layout:

```text
Transversa/
  shared/src/commonMain/kotlin/
  shared/src/commonTest/kotlin/
  shared/src/androidMain/kotlin/
  shared/src/iosMain/kotlin/
  androidApp/
  iosApp/Transversa.xcodeproj
  iosApp/Transversa/  # SwiftUI app, screens, adapters
  native/ffmpeg/android/
  native/ffmpeg/ios/
  docs/
```

Configure iOS device and simulator architectures supported by the current Kotlin version; don't ship simulator binaries in the App Store app. Expose stable Swift-friendly APIs for settings, presets, capabilities and conversion state. Where Kotlin `Flow`/suspend APIs are awkward for Swift, add a maintained compatible bridge or an explicit adapter with cancellation and lifecycle handling.

## 3. Run and debug

1. Open `iosApp/Transversa.xcodeproj` or its workspace if generated by your integration.
2. Select a simulator, development team and unique bundle ID, then build/run in Xcode.
3. Select a physical iPhone to verify native codec operation, imports, exports, memory pressure, cancellation and background behavior.
4. Debug Swift in Xcode; debug Kotlin shared logic with tests and available Kotlin tooling. Preserve FFmpeg native debug symbols for development and archive dSYM files for releases.
5. Run shared tests through Gradle using the exact task names generated by the configured KMP targets (`./gradlew :shared:tasks --all`); run iOS UI/integration tests through an Xcode test scheme (`xcodebuild test -project iosApp/Transversa.xcodeproj -scheme Transversa -destination 'platform=iOS Simulator,name=<installed device>'`) after configuring the project and scheme.

Use Instruments for memory/CPU/energy profiling and verify conversion performance on devices rather than assuming simulator parity.

## 4. FFmpeg build and hardware acceleration on iOS

- Build FFmpeg and required third-party libraries **from pinned source** for iOS device architectures and, separately, simulator architectures. Package and link only compatible slices, using XCFrameworks where suitable.
- Enable `--enable-gpl`, `--enable-version3` where needed for the chosen compatible GPLv3 build, `--enable-libx264`, and `--enable-libx265`; do **not** use `--enable-nonfree`. Include necessary decoders, demuxers, muxers, image/audio encoders, filters and protocols. Verify resulting codec/encoder lists rather than trusting configure flags alone.
- Probe VideoToolbox availability for `h264_videotoolbox` and `hevc_videotoolbox` on actual hardware; implement software fallback to libx264/libx265 where viable. Hardware and software options differ: VideoToolbox uses supported bitrate/quality parameters, whereas software encoders can use CRF/presets.
- Bundle all required libraries inside the signed app; no downloading executable code or dynamically installed codecs. Review static/dynamic linking and platform restrictions with current Apple rules.
- Keep conversions on background execution queues while the app is active, show progress and cancellation, and define honest behavior when iOS suspends or terminates the app. **Do not promise Android-style indefinitely running foreground-service conversions on iOS.** Evaluate limited background task time and appropriate supported background processing only if justified; inform the user when the app must remain open.
- Verify correct output with FFprobe and playback on another iOS application. Test odd dimensions, rotation, metadata, HDR, audio-only, corrupt input, low disk space, unsupported hardware and large files.

## 5. iOS file access, preview and sharing

- Import with SwiftUI `fileImporter` or UIDocumentPicker; respect security-scoped URL access and `startAccessingSecurityScopedResource()`/`stopAccessingSecurityScopedResource()` where applicable.
- Stage non-seekable or ephemeral input into the app's private temporary directory when necessary; use streamed copies, storage-space checks, and reliable cleanup.
- Preview video/audio with AVKit/AVPlayer and images with SwiftUI/QuickLook; keep platform-specific preview behavior native.
- **Save** must first let the user choose the destination/name through a native document-export workflow, then perform conversion and deliver the result. Because `fileExporter` normally exports an already-existing file, implement a native destination selection/export coordinator or clearly document a staged conversion workflow that still respects the agreed Save-first contract. Do not silently convert before Save is tapped.
- **Share** converts to a private temporary result and presents the system share sheet (`UIActivityViewController` or suitable SwiftUI wrapper); retain the temporary file until sharing is complete. After success, permit Save and Share of the existing result without re-encoding.
- Preserve MIME/UTType metadata and use unique temporary filenames; clear old temporary files on safe lifecycle boundaries.

## 6. Signing, TestFlight and App Store submission

1. Create a unique bundle identifier and app record in App Store Connect; set display name **Transversa** and tagline **The ultimate converter** in suitable marketing metadata.
2. Configure Signing & Capabilities, team, entitlements, supported iOS deployment target, version/build numbers, icons, launch assets and required privacy strings.
3. Complete App Privacy declarations, required-reason API/privacy manifest review for applicable SDKs, encryption/export compliance questions, accessibility review, content rights and codec-patent assessment.
4. Archive a **physical-device Release** configuration using Xcode Product → Archive, validate and distribute to App Store Connect. Confirm no simulator slices are included.
5. Configure TestFlight internal testers, then external testers if desired (external beta review may apply). Test real-device conversions and file sharing across several devices.
6. Add store metadata, screenshots, support URL, privacy policy where required, license/source links and review notes. Submit a production build for App Review after validation.
7. Preserve signing/provisioning documentation, source revision, binary hashes, native build flags, notices, source archives and dSYM files per release.

For repeatable CI, use a dedicated macOS runner, secret-managed signing, and a pinned Xcode toolchain. Never commit certificates or App Store API private keys.

## 7. Licensing and App Store release gate

**Do not assume a GPLv3 application bundled with libx264/libx265 can be distributed through Apple's App Store without legal analysis.** The GPL's downstream rights, Apple's distribution terms, code signing and technical restrictions can raise compatibility questions. Before investing in a store release, obtain distribution-focused legal review and determine a compliant release path. Keep a separate, documented decision for any future alternative encoding configuration; do not silently remove mandatory codecs or change the project's licensing.

Deliver complete corresponding source for the exact distributed native components, build scripts, patches, notices and reproducibility instructions. Audit dependency compatibility and codec patents separately. FFmpeg license reference: https://ffmpeg.org/legal.html .

## 8. Release checklist

- [ ] KMP framework and SwiftUI app build on clean Mac with pinned toolchains.
- [ ] Simulator UI tests and real-device codec tests pass.
- [ ] Save-before-convert, Share-before-convert, progress/cancel and output reuse behave correctly.
- [ ] iOS interruption/background limitations are tested and disclosed.
- [ ] Source, third-party licenses, GPL/App Store legal review and patent review completed.
- [ ] Privacy, accessibility, signing, screenshots and TestFlight validation completed.
